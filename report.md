## Опис реалізації

Гібридний пайплайн (реалізований у модулі [src/hybrid.py](src/hybrid.py)) поєднує можливості компактної мовної моделі `qwen2.5:3b` та символьного SMT-розв'язувача Z3. Замість прямих міркувань над текстом задачі, пайплайн використовує двохетапну парадигму:

1. **Нейромережева формалізація:** LLM транслірує умову задачі у проміжне представлення (Intermediate Representation, IR) у форматі JSON (див. [Додаток А](#додаток-а-промпт-специфікації-json), [Додаток Б](#додаток-б-промпт-формалізатора), [Додаток В](#додаток-в-системний-промпт)).
2. **Детермінована валідація та символьне розв'язання:** Код на Python верифікує коректність IR за допомогою набору евристик та компіляції в Z3. Якщо знайдено помилки, виконується одноразовий повторний запит із чіткими інструкціями. Після валідації символьний розв'язувач Z3 детерміновано знаходить розв'язок.

### 1. Промпт формалізатора (FORMALIZER_PROMPT)

Промпт формалізатора (наведений повністю у [Додатку Б](#додаток-б-промпт-формалізатора)) є центральним елементом підготовки даних для Z3. У заголовках логічно поділених блоків правил та прикладів використано прямі запитання в дужках:

- `2. True / False Puzzle Logic (Is A Attribute?, Is B Attribute?):`
- `3. Time,Slot, Week Puzzle (When?):`
- `4. Example Logic Puzzle (What is order?):`
- `5. Example Slots Puzzle (When? Which slot does fit?):`

Наявність прямих запитань у заголовках блоку може активувати механізм уваги моделі, що допомагає передбачати наступні токени. Коли модель читає конкретне формулювання на зразок _"When does each meeting take place?"_ або _"Who is a knight and who is a knave?"_, це створює семантичне тяжіння.

Окрім цього, такі запитання забезпечують розмежування просторів представлення, допомагаючи моделі зрозуміти природу невідомих. Питання формату `Is A Attribute?` спрямовують модель трактувати сутності як булеві змінні з бінарним доменом `[0, 1]`. Водночас запитання на кшталт `When?` або `What is order?` сигналізують про те, що змінні позначають координати або слоти впорядкованого простору, для яких необхідні спеціальні арифметичні відношення, такі як `% K`, `// K`.

#### Порядок блоків

Послідовність викладу інструкцій у промпті має строгу ієрархію:

1. **"1. Variable Domains & Mapping" (Фундаментальний базис):** Першим розташовано блок визначення змінних та їхніх числових меж (`[0, total_slots - 1]`). Без попереднього чіткого визначення простору змінних жодне логічне чи арифметичне обмеження не матиме коректного сенсу.
2. **"2. True / False Puzzle Logic" (Базова булева логіка):** Блок описує логічні зв'язки для бінарних задач (лицарі/брехуни, наявність атрибутів). Він передує складній арифметиці, оскільки вводить критичне для SMT-розв'язувача правило: **заборону використання `all_different` для бінарних змінних**, що запобігає перетворенню системи умов на безумовно нездійсненну.
3. **"3. Time,Slot, Week Puzzle" (Арифметичні шаблони планування):** Складніша арифметика слотів (визначення частин доби через оператор залишку від ділення `variable % K == 0/1`, відношення днів через цілочисельне ділення `A // K == B // K`). Ці правила спираються на діапазони змінних, "засвоєні" моделлю у пункті 1.
4. **"4–6. Few-shot приклади" (Ілюстрація правил):** Приклади слідують **після** абстрактних правил. Це дозволяє моделі спочатку сприйняти правила мови IR, а потім побачити їх цілісне втілення у синтаксично правильному JSON.
5. **Розміщення `{feedback}` наприкінці:** Змінна для зворотного зв'язку розміщена у самому кінці промпту. Через властивість recency bias у трансформерах контекст, розташований безпосередньо перед зоною генерації виходу, чинить найбільший вплив на модель під час повторної спроби.

#### Few-shot приклади

Для невеликої моделі звичайний текстовий ланцюжок думок у довільній формі не підходить: модель пише багато зайвого тексту, перевищує ліміт токенів та ламає формат JSON. Натомість тут послідовність міркувань закладена в саму структуру вихідного документа:

- спершу визначаються сутності та їхні числові межі у блоці `variables`;
- далі задаються групи взаємно виключних змінних у `all_different`;
- наприкінці формується список `constraints`, де кожне правило умови перетворюється на окрему математичну формулу.

Такий порядок є важливим для малої моделі, яка генерує текст послідовно. Коли змінні описані на початку, модель уже зафіксувала їхні назви у пам'яті (KV-кеші) та намагається не вигадувати зайвих або спотворених імен вже під час запису формул. Крім того, послідовний переклад правил (одне речення умови - один рядок обмеження) вчить модель вирішувати задачу крок за кроком, а не намагатися вгадати відповідь одразу.

Для компактної моделі кожен доданий приклад є досить дорогим з точки зору ресурсів, проте дає вирішальну практичну користь:

- **Чому це дорого:** кожен повний приклад містить текст задачі, схему JSON і багато обмежень, що забирає досить багато токенів. Тож, при ліміті контексту у 2048 токенів це зменшує вільне місце для тексту помилок під час повторної спроби. Також довгий промпт розсіює увагу моделі, через що вона може випадково скопіювати константи чи імена з прикладу в нову задачу.
- **Чому це корисно:** мала модель без прикладів (у режимі zero-shot) не здатна самостійно перекласти складні правила на мову цілочисельних формул Z3. Без зразка вона часто вигадує текстові значення, дійсні числа або зайві допоміжні змінні, через що розв'язувач відхиляє задачу.

#### Розбір прикладів за типами задач

##### 1. Задачі на порядок і лінійне розташування (What is order?)

Цей клас задач ілюструє приклад розстановки чотирьох книг на полиці (`4. Example Logic Puzzle (What is order?)`), взятий із набору [Задача D4. Bookshelf](problems/team-D.md#задача-d4-bookshelf). Первинний варіант було запропоновано моделлю, після чого внесено правки для формування правильного зразка в контексті. Приклад відповідає [задачі H2](problems/team-H.md#задача-h2-train-carriages) нашого набору (пасажири у чотирьох вагонах поїзда).

Змінні позначають сутності, а їхні значення - числові позиції на шкалі `[1, N]` або `[0, N-1]`. Щоб кожна позиція була зайнята лише одним об'єктом, обов'язково застосовується група `all_different`. Типові відношення перекладаються простими математичними формулами:

- крайні позиції записуються як `x == 0 or x == max`;
- безпосереднє слідування задається кроком `novel == dictionary + 1`;
- сусідство двох об'єктів перевіряється через модуль відстані `abs(A - B) == 1`;
- відносний порядок позначається нерівністю `atlas < novel`.

##### 2. Задачі на календарне та сіткове планування (When? Which slot does fit?)

Цей клас представлено прикладом розкладу шести зустрічей з понеділка по середу (`5. Example Slots Puzzle (When? Which slot does fit?)`), взятим із набору [Задача B3. Meeting week](problems/team-B.md#задача-b3-meeting-week). Він прямо відповідає [задачі H1](problems/team-H.md#задача-h1-project-week-schedule) нашого набору, де сім зустрічей розподіляються на вісім слотів тижня за наявності одного порожнього слота.

Для формалізації двовимірна сітка «дні $\times$ час доби» зводиться до одновимірної числової шкали слотів `[0, total_slots - 1]`. Число $K$ визначає кількість періодів на день (наприклад, $K = 2$ для ранку та дня). Зустрічі об'єднуються в `all_different`, а порожній слот розв'язувач знаходить автоматично, оскільки кількість доступних слотів більша за кількість зустрічей. Часові правила транслюються за допомогою простих арифметичних операцій:

- час доби визначається залишком від ділення: `meeting % K == 0` для ранку та `meeting % K == 1` для дня;
- зустрічі в межах одного дня мають однакову частку: `A // K == B // K`;
- наступний день позначається додаванням одиниці: `B // K == (A // K) + 1`;
- раніший день записується строгою нерівністю часток: `A // K < B // K`.

### 2. Валідатор IR (validate_ir)

Етап валідації, а саме функція `validate_ir` у гібридному пайплайні ([src/hybrid.py](src/hybrid.py)), здійснює багаторівневу перевірку проміжного представлення до його передачі у Z3.

#### Короткий опис кожного етапу валідації:

1. **Валідація назв змінних (`is_valid_variable_name` та `sanitize_variable_name`):**
   Перевіряє відповідність імен змінних допустимим ідентифікаторам Z3/Python за регулярним виразом `^[a-zA-Z_][a-zA-Z0-9_]*$`. Забороняє пробіли, дефіси, спеціальні знаки та цифри на початку ідентифікатора.
2. **Валідація структури та меж доменів (`variables`):**
   - Для дискретних множин `{"values": [...]}`: перевіряє, що список не є порожнім і містить виключно цілі числа (`int`).
   - Для діапазонів `[lo, hi]`: перевіряє цілочисельність та правильність порядку меж (`lo <= hi`). Виявляє випадки, коли модель переплутала верхню і нижню межі або помилково передала одноелементний список.
3. **Перевірка оголошення змінних (`uncreated_vars`):**
   Перевіряє, щоб кожна змінна, задіяна у групах `all_different`, була заздалегідь явно оголошена у словнику `variables`.
4. **Валідація розмірів груп взаємної винятковості (`check_all_different_group_sizes`):**
   Переконується, що кожна група в `all_different` містить щонайменше 2 змінні. Порожні або одноелементні групи не мають математичного сенсу для предиката `Distinct` у Z3 та відхиляються із порадою об'єднати взаємовиключні сутності в одну спільну групу.
5. **Санітизація бінарних змінних у `all_different` (`sanitize_all_different_binary_vars`):**
   Перевіряє відсутність змінних із бінарним доменом `[0, 1]` у групах `all_different` для задач без оптимізації. Оскільки в бінарних задачах більше ніж дві змінні не можуть бути попарно різними, наявність трьох і більше бінарних змінних у `all_different` гарантовано робить систему обмежень суперечливою (UNSAT).
6. **Верифікація побудови абстрактного синтаксичного дерева Z3 (`ir_solver.build(ir)`):**
   Здійснює пробну компіляцію у Z3 безпосередньо у блоці `try/except`. Z3 перевіряє коректність синтаксису формул, виявляє невідомі змінні у виразах `constraints`, заборонені оператори або неприпустимі функції (дозволено лише `abs()`).

#### Підхід Instruction замість Error

Принциповим архітектурним рішенням валідатора є формування **направлених інструкцій замість звичайних повідомлень про помилки**:

- Замість констатації факту помилки:
  > `Error: invalid range for 'kickoff': [7, 0]`
  > валідатор генерує пряму команду до дії:
  > `Swap bounds for 'kickoff' variable ONLY so lower bound comes first: [0, 7].`
- Замість:
  > `Error: undefined variables in all_different`
  > валідатор надсилає точну вказівку:
  > `Add variables to 'variables': demo, legal`
- Замість:
  > `Error: distinct constraint impossible on boolean domain`
  > валідатор формує однозначну команду:
  > `Remove "all_different": [...] field from previous IR JSON.`

Це важливо для нашого випадку, бо компактні мовні моделі мають обмежені аналітичні можливості та схильні до галюцинацій при спробі інтерпретувати абстрактні системні помилки. Отримавши абстрактне повідомлення про помилку, мала модель часто не здатна вивести з нього алгоритм корекції та або повторює ту саму помилку, або ламає інші частини JSON.

### Механізм повторної спроби (Retry)

У функції `solve(problem)` реалізовано контрольований одноразовий цикл повторної спроби (single retry with feedback):

1. **Перший прохід:** Пайплайн запускає `ir = formalize(problem)` без додаткового контексту.
2. **Перевірка:** Отриманий IR проходить через `validate_ir(ir)`. Якщо список повідомлень порожній (`errors == []`), IR вважається валідним і одразу спрямовується до `run_solver`.
3. **Повторний запит у разі збою:** Якщо валідатор виявив помилки, формується рядок інструкцій `feedback`:

   ```
   Previous attempt was rejected though errors.
   Instructions:
   <перелік сформованих інструкцій>

   Read each instruction/error message above and fix/follow instruction
   ```

   Цей блок передається у `formalize(problem, feedback=...)`. Модель отримує оригінальний текст задачі разом із чітким переліком виправлень, які необхідно внести.

## Аналіз відмов

Відповідно до зазначених правил встановлено такі причини невдалих запусків:

1. **Відмови монолітного конвеєра:**
   - **H1 (код M-R):** у першому прогоні модель у полі `trace.reasoning` призначає Kickoff та Architecture на однаковий час (понеділок ранок), порушуючи умову 1 («кожна зустріч займає один слот»), а також розміщує Demo у середу замість вівторка, порушуючи умову 3. У другому прогоні модель самосуперечливо розміщує Hiring на ранок вівторка, прямо порушуючи умову 7 щодо обов'язкового денного слота.
   - **H2 (коди M-R, M-S):** у першому прогоні модель порушує умову 2 («Kharyton travels in carriage 2»), розмістивши Харитона одночасно у вагонах 1 та 4, що також порушує унікальність пасажирів (код M-R). У другому прогоні міркування раптово обірвано, і модель безпідставно заявляє про множинність розв'язків (`status: "multiple"`) із порожнім словником розв'язку (код M-S).
   - **H4 (коди M-S, M-R):** у першому прогоні модель не змогла довести єдиність конфігурації і хибно заявила про статус `multiple` (код M-S), а у виданому розв'язку призначила Федору лицарем, що прямо суперечить її заяві про брехливість Устима (код M-R).

2. **Відмови гібридного конвеєра:**
   - **H1 (код H-F):** невідповідність обмежень тексту задачі. У `trace.attempts[0].ir.constraints` модель записала спільний день `architecture // 2 == demo // 2`, але опустила ранковий слот `architecture % 2 == 0` та денний слот `hiring % 2 == 1`. Оскільки ці вимоги містяться безпосередньо в тексті задачі, пропуск є саме H-F (а не фоновим знанням H-K). Через це Z3 знайшов два варіанти розкладу й повернув статус `multiple`. У першому прогоні знайдений `first_solution` порушив умову ранку, що додатково підтверджує хибність самої системи умов.
   - **H2 (код H-F):** викривлення логічних формул і простору змінних. Модель об'єднала 14 різнорідних сутностей в одну групу `all_different` для домену з 5 значень, що створило математично суперечливу систему, а відношення сусідства вагонів записала через додавання замість модуля різниці. Як наслідок, Z3 зафіксував нездійсненність системи (`status: "none"`).
   - **H3 (код H-F):** у першому прогоні модель не формалізувала пряму вимогу «кожен виправив щонайменше 1 баг» і встановила межу `[0, 10]`, через що Z3 включив варіант із нулем для Віри і видав статус `multiple`. У другому прогоні IR містив інвертований діапазон `daryna: [4, 2]` та пропуск суми `sum == 10`, що призвело до статусу `none`.
   - **H4 (коди H-F, H-P):** при формалізації мовна модель підмінила змістовні висловлювання жителів тривіальними тавтологіями `X == 1 or X == 0` (код H-F). На етапі оформлення `present()` модель отримала результат Z3 `{Taisiia: 1, Ustym: 0, Fedora: 0}`, але спотворила його інтерпретацію, зіставивши 1 із брехуном, а 0 із лицарем, і помилково зробила Федору лицарем (код H-P).
   - **H5 (код H-F):** невідповідність у виборі простору змінних. Змістовно задача розв'язана абсолютно точно: обидва запуски згенерували еталонний розподіл (`Vlad: Dell`, `Yana: ThinkPad`, `Zoriana: MacBook`), що повністю збігся зі змістом `first_solution`. Проте в IR модель оголосила змінні з доменом `[0, 2]` не лише для людей, а й окремо для ноутбуків (`thinkpad`, `macbook`, `dell`), не пов'язавши останні жодним обмеженням. Наявність незв'язаних змінних згенерувала 27 допустимих комбінацій у системі, через що Z3 повернув статус `multiple` замість `unique`.

### Детальний розбір показових відмов

#### 1. Монолітний конвеєр: порушення умов задачі в міркуванні H2 (Run 1, помилка M-R)

У задачі H2 про розміщення чотирьох пасажирів у чотирьох вагонах пряма умова тексту стверджує: _«Kharyton travels in carriage 2»_. У полі `trace.reasoning` монолітна модель спочатку формально повторює умову, проте на етапі зіставлення атрибутів повністю втрачає логічну послідовність:

```json
"1": {"Name": "Kharyton", "Destination": "Kyiv", "Luggage": "suitcase", "Book": "poetry"},
"2": {"Name": "Tsvitana", "Destination": "Dnipro", "Luggage": "backpack", "Book": "fantasy"},
"3": {"Name": "Ustyna", "Destination": "Lviv", "Luggage": "guitar case", "Book": "history"},
"4": {"Name": "Kharyton", "Destination": "Kyiv", "Luggage": "guitar case", "Book": "thriller"}
```

Пасажир Харитон одночасно призначається у перший та четвертий вагони з різними наборами речей, а вагон 2 віддається Цвітані. Це демонструє характерну відмову M-R: під час зіставлення кількох категорій компактна модель 3B не утримує інваріанти у робочій пам'яті й робить фактичні помилки прямо у процесі міркування.

#### 2. Гібридний конвеєр: пропуск складеної умови в тексті H1 (Run 1, помилка H-F)

У задачі H1 розв'язувач Z3 відпрацював коректно відповідно до наданого IR, проте результат повернув статус `multiple` через семантичний дефект у списку обмежень `trace.attempts[0].ir.constraints`:

```json
"constraints": [
  "kickoff == 0",
  "wrap_up == 7",
  "architecture // 2 == demo // 2",
  "legal // 2 == architecture // 2 + 1",
  "marketing // 2 == legal // 2",
  "legal % 2 == 1",
  "hiring // 2 < demo // 2"
]
```

Текст задачі чітко зазначає: _«Architecture and Demo take place on the same day; Architecture is in the morning.»_ Модель формалізувала спільний день (`architecture // 2 == demo // 2`), але пропустила вимогу ранкового слота (`architecture % 2 == 0`). Оскільки факт міститься безпосередньо в тексті, це класифікується як помилка формалізації H-F, а не брак знання H-K. Розв'язувач знайшов два допустимі варіанти для вівторка (ранковий і денний), через що система детерміновано зафіксувала неєдиність розв'язку.

## Висновки

У ході практичного дослідження порівняно два принципово різні підходи до розв'язання логічних задач на базі локальної моделі `qwen2.5:3b`: пряме текстове міркування (монолітний конвеєр) та нейросимвольний розподіл праці (гібридний конвеєр із SMT-розв'язувачем Z3).

Результати експерименту продемонстрували фундаментальні межі монолітного підходу. Компактна модель непогано впоралася з простими задачами на нерівності та базове зіставлення (H3, H5), проте повністю відмовила на складних комбінаторних сітках (розклад H1, вагони H2). Моноліт не здатний утримувати глобальні інваріанти задачі у своїй робочій пам'яті: він плутає час доби, призначає різні події в один слот або клонує одну й ту саму сутність у кілька позицій.

Гібридний конвеєр пропонує значно потужнішу архітектуру, оскільки позбавляє мовну модель необхідності самостійно виконувати комбінаторний перебір та арифметичні обчислення. Усі розрахунки, перевірка несуперечливості та доведення єдиності розв'язку делегуються символьному розв'язувачу Z3, який працює детерміновано, швидко (до кількох мілісекунд) і без математичних помилок.

Водночас дослідження виявило головне "пляшкове горло" гібридного конвеєра - критичну залежність від точності первинної формалізації тексту в IR. Компактній моделі на 3 млрд параметрів бракує семантичної уваги для безпомилкового перекладу складних складених речень: вона або втрачає окремі під-умови (як ранковий слот у задачі H1), або обирає невідповідний простір змінних (небінарні змінні в H5). Навіть якщо ядро Z3 працює бездоганно, найменший семантичний дефект у згенерованому IR призводить до повної відмови системи.

IR_SPEC = """IR format (JSON):
{
  "variables": {"<name>": [min, max] for CONTINUOS VALUES or {"values": [a, b, c]} for EXPLIT SET or {"values": [a]} for ONLY ONE or [0, 1] }, integer variables and their domains
  "all_different": [["<name>", ...], ...], OPTIONAL: groups whose values must all differ
  "constraints": ["<expression>", ...], every expression must be true

}

String and symbolic values are FORBIDDEN.
Inside arithmetic a comparison counts as 1 (true) or 0 (false), e.g. "(A == 1) + (B == 1) == 1".
Variable names must be identifiers: letters, digits and underscores only, no spaces, e.g., meeting_kickoff, role_alice."""
